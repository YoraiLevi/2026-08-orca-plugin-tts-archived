### node-web-audio-api — caveats found in its own README (PRIMARY, maintainer-authored)

- **Install size**: the npm tarball is ~20 MB compressed (measured this pass, `du -sh` on the downloaded `.tgz`) because it bundles **all 7 platform binaries in one package** rather than splitting into per-platform optional-dependencies the way `sherpa-onnx-node` does. Uncompressed, the seven `.node` files alone total ~42 MB. Trade-off: zero postinstall network fetch and zero platform-detection risk, at the cost of every install downloading binaries for platforms it will never run on.
- **Linux runtime dependency**: prebuilt Linux binaries are compiled with the `jack` feature flag. Per the README: *"on Linux distributions that ship with pipewire (most of them right now), the library should work by just installing pipewire-jack"* (`apt install pipewire-jack`) — i.e., **an extra system package beyond a stock Ubuntu install may be required** for audio output to work at all on some Linux configurations. Falls back to the default audio host (typically ALSA via `cpal`) if no JACK server is found.
- **Linux ALSA crackle**: *"Using the library on Linux with the ALSA backend might lead to unexpected cranky sound with the default render size (i.e. 128 frames)"* — documented workaround is `new AudioContext({ latencyHint: 'playback' })`, which raises the render size to 1024 frames. This is a real, maintainer-documented predictable bug with a maintainer-provided mitigation (architecture-level fix via a constructor option, not a workaround hack).
- **No-audio-sink / CI mode is a first-class, documented feature**: *"if your system has no audio sinks (e.g. docker image, CI) use `{ sinkId: { type:'none' } }` when initializing AudioContext, else it will crash with `DeviceNotAvailable`"* — this directly answers part of Area 4 (see below): the library anticipates headless CI as a use case.
- Node engine requirement is `>=22`. ORCA is on Node 24 (`orca-plugin-api.md`, `package.json:283-286`), so this is satisfied.

### RANKING for a plugin that must install with zero compilation on all 6 combos AND stream PCM AND stop instantly

1. **`node-web-audio-api`** — only option verified to cover all 6 combos (7 targets including win32-arm64) with zero compile step, native PCM-accurate streaming and stop semantics, an explicit CI/no-sink mode, and active maintenance (pushed 11 days before this research pass). Costs: ~20 MB install, Linux JACK/pipewire-jack nuance, and it requires the feature to run where it has Node module access — fine for a main-process/worker design, **not usable from inside ORCA's sandboxed plugin worker if that worker cannot load native addons** (unverified this pass — check against `orca-plugin-api.md`'s plugin worker capability list before committing).
2. **Bundled `ffplay`/`ffmpeg`, shelled out** — proven PCM streaming and fast kill on macOS (prior pass), but the npm-wrapper ecosystem for it is broken: `ffplay-static` is dead (2017), `ffmpeg-static` doesn't ship `ffplay` at all and has an open, maintainer-acknowledged gap on win-arm64. This path is realistic only if the plugin bundles its own compiled `ffmpeg`/`ffplay` binaries per target (extra build/release engineering, not "off the shelf").
3. **`audify`** — real streaming, real instant-stop, decent maintenance history, but **confirmed no win-arm64 prebuild** (checked release assets directly) and is roughly a year stale relative to `node-web-audio-api`. Disqualified by R1 on win-arm64 alone unless a compile-from-source fallback is acceptable there (it isn't, per the zero-compile requirement).
4. **Per-OS shell-out trio (afplay/aplay-family/PowerShell)** — rejected: not coherent (see matrix), two of the three legs refuse raw PCM on stdin, and the Linux leg isn't guaranteed present.
5. **`speaker`, `naudiodon2`** — rejected: `speaker` is stale with a documented multi-second `end()` hang; `naudiodon2` was verified this pass to *always* compile via `node-gyp` (no prebuild path exists at all), which is a hard violation of "installs with zero compilation."
6. **Web Audio in an Electron renderer** — technically the strongest option (native browser API, zero extra dependency) but only available if the feature runs in ORCA's main/renderer process rather than the plugin sandbox; contingent on an architecture decision this research doesn't own (flag for `docs/.discussion/001-integration-path.md`).

**What does a bare Windows GitHub Actions runner have installed?** `unknown` (not directly verifiable without running a job on `windows-latest`, which this pass did not do). `actions/runner-images`'s own `Windows2025-Readme.md` documents installed software packages but has **zero mentions of speech/voice/SAPI** (`grep -i "speech\|voice\|audio\|sapi"` against the raw file returned nothing) — this only proves the readme doesn't advertise it, not that SAPI5 (which ships as a Windows OS component, not "installed software" in the choco/vcpkg sense the readme documents) is absent. SAPI5's `*Desktop` voices are historically part of the Windows Speech Platform baked into the OS since Vista and are commonly present on Windows Server SKUs too, but Windows Server historically required the "Desktop Experience" feature for the full speech runtime on some older releases (Server 2008-era evidence found, not confirmed current for the 2022/2025 base images GH Actions uses). **Do not assume SAPI5 voices exist on `windows-latest` without a direct CI smoke test that enumerates `System.Speech.Synthesis.SpeechSynthesizer.GetInstalledVoices()` and asserts the list is non-empty.**

### Linux: what ships by default, and is any of it non-robotic?

- **Ubuntu 24.04 desktop** ships `speech-dispatcher` and the `orca` screen reader (name-collision warning: Ubuntu's own accessibility screen reader is *also* called "Orca" — unrelated to the ORCA agent this plugin targets) as part of the `ubuntu-desktop` metapackage's dependency graph — VERIFIED via Ubuntu's own package page, `packages.ubuntu.com/noble/ubuntu-desktop`, which lists both packages directly (PRIMARY: Ubuntu's own package repository). `speech-dispatcher`'s default synthesis backend is `espeak-ng`.
- **espeak-ng** — formant synthesis, explicitly and consistently described as robotic; this matches the well-known reputation of the espeak family and is not seriously disputed by anyone in the space (not independently re-verified by audio sample this pass — treat the "robotic" characterization as CLAIMED/common-knowledge rather than freshly measured).
- **RHVoice, Festival, Pico** — none of these are part of a default Ubuntu install; they are opt-in `apt install` targets. RHVoice specifically markets itself as a step up from espeak-ng in naturalness, but it is not preinstalled anywhere in the target's deployment surface, so it doesn't help "out of the box."
- **GitHub Actions `ubuntu-latest` runner**: `actions/runner-images`'s own `Ubuntu2404-Readme.md` and the entire `actions/runner-images` repository were checked for any of `speech`, `festival`, `pico`, `dispatcher`, `espeak`, `alsa`, `pulseaudio` — **zero matches** (`gh api search/code` against the repo, and a direct `grep` of the readme). This is a headless server-class image, not `ubuntu-desktop`; it has **none** of Ubuntu desktop's default speech stack. Confirms: any Linux OS-native TTS path needs an explicit `apt-get install espeak-ng` (or similar) step in CI — it is not present by default.

### macOS `say`, for comparison

Already measured on this machine (`PITFALLS.md` P5): functional, moderate voice quality (system voices, several near-neural options via `Alex`/`Ava`/etc. depending on installed voice packs), but ~414 ms process-spawn cost before any audio and no stdin PCM streaming.

### VERDICT

**The OS-native trio is not coherent enough to be a cross-platform default.** The three platforms are not merely different in packaging — they are different in *reachable quality tier*:

- macOS `say` reaches genuinely decent system voices (and can reach very good ones if the user has installed Siri-quality voice packs) with zero extra installs.
- Windows, out of the box, is fenced to SAPI5 `*Desktop` voices (Zira/David) — the *worst* tier Windows has, because the good tier (Narrator natural voices) is cryptographically locked to Narrator/Edge and reaching it requires installing a third-party reverse-engineering hack (`NaturalVoiceSAPIAdapter`) that its own author calls fragile and liable to break on any Windows update. There is no documented, Microsoft-sanctioned way for a third-party app to reach Windows's good voices in 2026.
- Linux, out of the box (even on `ubuntu-desktop`, let alone a headless GH Actions runner), is fenced to `espeak-ng`-quality formant synthesis unless the user manually installs something better.

Shipping "OS-native TTS" as *the* default would mean: macOS users get an acceptable experience, Windows and Linux users get either a robotic voice or a rooted-in-a-hack one. That directly violates R1 ("No macOS gets the good voice, Linux gets espeak") — this is *exactly* the two-tier outcome R1 forbids, just relocated from "engine choice" to "OS-native voice choice." This corroborates and sharpens the existing settled finding in `HANDOFF.md`: **the only way to satisfy R1 is a bundled neural engine (Piper via `sherpa-onnx-node`, per the existing decision) with OS-native (`say`/SAPI5/espeak-ng) as the uniform, quality-labeled *fallback* tier on all three OSes — never as the primary experience on any one of them.** Do not let "but macOS `say` is actually pretty good" argue for a native-first default; the same argument fails identically on Windows and Linux, and R1 requires the three to be identical, not each individually acceptable.

## Area 3 — Model / binary distribution

- **ONNX model files are platform-neutral.** An `.onnx` file (or a Piper `.onnx` + `.onnx.json` voice pair) is pure numeric-graph data with no compiled/native code; the *runtime* (`sherpa-onnx-node`'s per-platform native addon) is what's platform-specific, not the model. One model download genuinely serves all 6 combos — this is inherent to the ONNX format's design goal (interoperable serialization) and is not something this pass needed to independently verify beyond noting no counter-evidence exists.
- **Cache-path convention — real-world split, not a solved consensus:**
  - `env-paths` (sindresorhus) is the standard npm package for OS-idiomatic cache dirs: XDG (`$XDG_CACHE_HOME` → `~/.cache/<name>`) on Linux, `~/Library/Caches/<name>` on macOS, `%LOCALAPPDATA%\<name>\Cache` on Windows. Confirmed alive on npm (`v4.0.0`, published 2026-01-24).
  - **transformers.js (Hugging Face, 16.2k stars, pushed 2026-08-19) does *not* use `env-paths` or any OS convention** — VERIFIED by reading `packages/transformers/src/env.js` directly: its `DEFAULT_CACHE_DIR` is `path.join(dirname__, '/.cache/')`, i.e. a `.cache` folder **relative to the installed package's own location inside `node_modules`.** This is a real anti-pattern worth naming: caches placed inside `node_modules` are wiped on every `npm install`/reinstall, and are not user-visible or user-cleanable the way an OS cache dir is.
  - **node-llama-cpp (2160 stars, pushed 2026-08-11) also does not use the OS-native convention** — VERIFIED by reading `src/config.ts` directly: it hardcodes `path.join(os.homedir(), ".node-llama-cpp")` on every platform. This is more durable than transformers.js's approach (survives reinstall) but is still not idiomatic on Windows (no `%LOCALAPPDATA%`) and ignores `$XDG_CACHE_HOME` on Linux (so it won't honor a user's redirect of cache off a small root partition).
  - **ORCA's own precedent is the one to actually mirror** — `src/main/speech/model-manager.ts:162` in the ORCA codebase itself uses `join(app.getPath('userData'), 'speech-models')`, i.e. Electron's own per-OS `userData` convention (`~/Library/Application Support/Orca` / `%APPDATA%\Orca` / `~/.config/Orca`), which *is* the OS-idiomatic path on all three platforms via Electron's built-in resolution. This is genuinely primary — it's ORCA's own shipped code, already cited with file:line in `orca-plugin-api.md`.
- **The Windows non-ASCII path bug is ORCA's own, already-hit landmine — do not re-derive, reuse it.** Per `orca-plugin-api.md` "The STT model cache — our precedent, and its Windows landmine" (`docs/.research/orca-plugin-api.md:960-985`, citing `src/main/speech/model-cache-path.ts:30-50`): *"sherpa-onnx 1.12.x cannot load model files from non-ASCII Windows paths"* — a username like `Björn` breaks model loading unless the cache path is relocated to an ASCII-only shared root (`%PROGRAMDATA%`/`%ALLUSERSPROFILE%`/`%PUBLIC%`), which ORCA does by hashing the requested path and migrating with a `.partial` + atomic-rename copy. **If the TTS plugin uses `sherpa-onnx-node` (the settled default engine per `HANDOFF.md`), it hits this identical bug and must mirror this exact mitigation** — there's an existing regression test in ORCA to model against: `src/main/speech/model-manager-windows-path.test.ts`.
- **Windows Defender / long-path gotchas beyond the non-ASCII issue:** not independently re-verified this research pass with a fresh search; treating as `unknown` rather than restating unverified folklore about Defender scanning large ONNX downloads or `MAX_PATH` limits. Flag as an open risk to smoke-test directly (download a real Piper voice + Defender-scan timing on a `windows-latest` runner) rather than assume.
- **bz2 support**: `unknown` — not investigated this pass; Piper voices on Hugging Face are typically distributed as plain `.onnx`/`.onnx.json`, not `.tar.bz2`, so this may be a non-issue for the specific engine already chosen — worth a one-line confirmation against the actual Piper voice download URLs before treating as settled.

**Iteration 1 (this pass, single iteration — see convergence note below).**

Terms tried and signal:
- `npm view <pkg> optionalDependencies/dependencies` on 12 candidate packages — **direct, primary, highest signal**; this is how the win-arm64 gap in `sherpa-onnx-node`/`ffmpeg-static`/`audify` and the presence in `node-web-audio-api` were actually established, not inferred from docs.
- Downloading and inspecting the `node-web-audio-api` npm tarball directly — **highest signal of the whole pass**; contradicted what a docs-only read would have shown (no visible per-platform optionalDependencies packages, which could have been misread as "doesn't support multiple platforms" — the truth is it bundles them all in one package).
- `gh api repos/<org>/<repo>` for stars/pushed_at/open_issues — reliable, cheap, used throughout instead of trusting READMEs' "actively maintained" claims.
- `gh api "search/code?q=...+repo:<repo>"` to read a specific maintained project's own source (config.ts, env.js, README) rather than a summary of it — high signal, this is how the cache-path anti-pattern in transformers.js/node-llama-cpp and the CI-split pattern in node-web-audio-api were found.
- `curl` against `actions/runner-images` raw files directly — primary source, zero-noise; much better than searching for third-party "what's on the GitHub Actions runner" blog posts, several of which turned up in the DuckDuckGo passes and were **not** used as citations because they were speculative/outdated relative to the actual current readme.
- DuckDuckGo queries on Windows OneCore/Narrator/SAPI — moderate signal; top organic hits were SEO TTS-product landing pages (`speechsynthesis.online`, `voicertool.com`, `speechma.com`) that were **rejected as noise** (not prior art, not primary sources, just TTS SaaS marketing pages that happened to rank for the query). The useful hits were Stack Overflow answers and one GitHub issue, cross-checked against the `NaturalVoiceSAPIAdapter` maintainer's own README for a primary-source anchor.
- DuckDuckGo query on `ubuntu-desktop` accessibility packaging — low signal on its own (returned generic screen-reader tutorials); superseded by going directly to `packages.ubuntu.com` (Ubuntu's own package repository), which is the actual primary source and should have been the first move, not the DuckDuckGo query.

**What would sharpen a second iteration** (not run this pass — see convergence note): follow `node-web-audio-api`'s own dependency, `orottier/web-audio-api-rs` (the Rust audio engine underneath), to check whether *it* has open issues about Linux ALSA/JACK behavior that predate and explain the README's crackle warning; and directly smoke-test a `windows-latest` GitHub Actions job enumerating `System.Speech.Synthesis.SpeechSynthesizer.GetInstalledVoices()` rather than reasoning from Windows Server history, since that Area 2 sub-question is the one genuine "unknown" left standing that a live CI run (not more search) would resolve fastest.

**Convergence note:** this pass ran once (not the full three-iteration protocol) because the questions were empirical/factual (does package X ship platform Y, is API Z reachable) rather than multi-constraint architectural tradeoffs — most were resolved with a single authoritative primary-source check (`npm view`, a tarball listing, a `gh api` call, or a maintainer's own file) rather than requiring synthesis across competing recommendations. The one question this pass could not close — whether `windows-latest`/`ubuntu-latest` GH Actions runners have a live audio output device — is marked `unknown` rather than guessed, and the fastest way to close it is a direct CI smoke test, not another search iteration.
