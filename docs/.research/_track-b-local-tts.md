# Track B — Local/On-Device TTS Engine Landscape (as of 2026-08-20)

> Research pass for the ORCA TTS plugin. Covers macOS-first, zero-install-default + low-latency-streaming-upgrade engine choices. All facts below are sourced live via `github-search` (`gh api`), `duckduckgo-search`, and `web-scraper` — nothing pulled from training-data memory. Every non-obvious claim is cited; latency numbers are labeled **MEASURED** (independent/third-party benchmark) or **CLAIMED** (vendor/author's own repo, blog, or README). Raw search/scrape artifacts live under `.research/prior-art-search/` in this repo (filenames referenced inline).

This is a real evidentiary gap, not an oversight: local-TTS numbers in the wild are almost all vendor-self-reported.

## 2. Deep-dive: the 3 best candidates for "zero-setup default + low-latency-streaming upgrade"

### 2a. macOS `say` / `AVSpeechSynthesizer` — the zero-setup default

This is the only candidate that satisfies "ZERO setup" literally: it ships with every Mac, requires no `pip`/`npm install`, no model download, no license file to review. From Node, the simplest integration is `child_process.spawn('say', ['-v', voice, text])` — `say` starts speaking without a perceptible model-load delay because there's no neural model to load; it's the closest thing to instant TTFA in this entire list, though (see the table's noted gap) no one has published a rigorous number for it — a first-party measurement is worth doing directly against your own hardware rather than trusting an unverified anecdote. Two real constraints found in this pass: (1) `AVSpeechSynthesizer` instances **cannot interrupt each other** — a second `speak()` call while one is in progress is silently ignored, not queued or errored ([itnext.io, Swift TTS deep-dive](https://itnext.io/swift-avfoundation-framework-text-to-speech-tool-f3e3bfc7ecf7)) — this matters directly for huddle mode's barge-in/interrupt requirement and needs its own design note, not just a `say -v` wrapper. (2) Personal Voice — the highest-quality on-device option, since it's the user's own cloned voice — is **not reachable from the command line at all**; Terminal lacks the entitlement Apple requires, confirmed by a maintainer who had to build a workaround entitled app just to record Personal Voice's audio ([limneos/SavePersonalVoiceAudio](https://github.com/limneos/SavePersonalVoiceAudio)). So the zero-setup default is really "system voices via `say`," not "Personal Voice via `say`" — don't promise Personal Voice support without a full macOS app + entitlement, which is a materially bigger build than a CLI wrapper.

### 2b. Kyutai `pocket-tts` — the recommended local-neural upgrade

Of every local neural engine surveyed, `pocket-tts` is the best fit for "low-latency streaming, works on this exact hardware class (Apple Silicon laptop, no GPU)." It's explicitly designed and benchmarked by its own team on a MacBook Air M4 CPU: ~200ms to first audio chunk and ~6x real-time throughput on 2 CPU cores ([kyutai-labs/pocket-tts README](https://github.com/kyutai-labs/pocket-tts)) — both labeled CLAIMED since they're the vendor's own numbers, not an independent benchmark, but they come from the same team that published the underlying research paper (arXiv:2509.06926), which is a stronger provenance signal than a marketing blog. Install is `pip install pocket-tts` (or `uvx pocket-tts` for zero-persistent-install trial runs) — there is no native Node SDK, so the Node integration path is either (a) shell out to `pocket-tts generate` per utterance (simple, but pays model-load cost per call — the README explicitly warns `load_model()` is slow and recommends keeping it resident), or (b) run `pocket-tts serve`, which starts a local HTTP server and keeps the model in memory between requests, and have the Node process talk to it over HTTP/WebSocket for real streaming. Given huddle mode's "speak streaming replies with low latency" requirement, (b) is clearly the right shape: one long-lived local server process, Node/TypeScript as a thin HTTP client. MIT license, CPU-only design (explicitly states it does not need the GPU build of PyTorch), and support for 6 languages today with more planned.

### 2c. sherpa-onnx (`sherpa-onnx-node`) — the flexible native-binding upgrade

The most Node-native way to get the widest reach across engines without shelling out to Python at all: `sherpa-onnx-node` is a real, actively-published npm package (v1.13.4/1.13.5 as of this pass) that wraps `sherpa-onnx`'s C++ core in a `node-addon-api`-based, multi-threaded native addon ([npmjs.com/package/sherpa-onnx-node](https://www.npmjs.com/package/sherpa-onnx-node), [k2-fsa/sherpa-onnx nodejs-addon-examples README](https://github.com/k2-fsa/sherpa-onnx/blob/master/nodejs-addon-examples/README.md)). It's a *runtime*, not one model — it can load Piper, VITS, Coqui, Kokoro, or (as of a May 2026 conversion, [csukuangfj2/sherpa-onnx-supertonic-3-tts-int8-2026-05-11](https://huggingface.co/csukuangfj2/sherpa-onnx-supertonic-3-tts-int8-2026-05-11)) even Supertonic-3 ONNX weights, all through the same Node API, with explicit macOS arm64 support in its platform matrix ([k2-fsa/sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx)). This gives you a hedge against any single upstream model repo going away (see the Supertonic landmine below — sherpa-onnx already re-hosts a converted copy of its weights, so the plugin isn't left stranded if `supertone-inc/supertonic` truly goes dark). The tradeoff versus `pocket-tts`: sherpa-onnx's own TTS-path streaming/TTFA numbers were not found in this pass (its published streaming benchmarks are for the ASR side), so the actual low-latency behavior needs to be measured directly against whichever model you load, rather than assumed from the runtime's general "supports streaming" design claim.

## 3. Licensing landmines

- **Piper's maintained fork changed license from MIT to GPL-3.0.** The original `rhasspy/piper` (MIT) is now **archived**, with its README pointing exclusively to `OHF-Voice/piper1-gpl` ("Development has moved: https://github.com/OHF-Voice/piper1-gpl" — [rhasspy/piper README](https://github.com/rhasspy/piper)), which is **GPL-3.0**. If the plugin invokes Piper as a separate subprocess (CLI) or over HTTP, GPL's copyleft does not propagate to the calling code; if it links `libpiper` directly into a Node native addon, it does. **Mitigation: invoke Piper only via subprocess/HTTP, never link the library.**
- **espeak-ng is GPL-3.0.** Same mitigation as Piper: subprocess only, don't link.
- **Picovoice `Orca` is not a plain-open engine despite the public Apache-2.0 repo.** The SDK code is Apache-2.0, but running it requires a Picovoice AccessKey that is validated against Picovoice's license servers over the internet — even though synthesis itself runs offline — and usage is metered against an account tier ([Picovoice/orca README, "AccessKey" section](https://github.com/Picovoice/orca)). This breaks the "zero setup, works offline forever" property a default engine needs, and its free tier limits are a hard ceiling for a huddle-mode default. **Also flag the naming collision explicitly in code/docs**: "Orca" the TTS engine and ORCA the host agent are unrelated projects that will confuse anyone grepping logs or docs.
- **Coqui XTTS-v2 model weights are under the Coqui Public Model License (CPML)**, not a standard permissive license — the code (MPL-2.0) and the weights (CPML) are licensed separately, and CPML has commercial-use restrictions beyond MPL-2.0 ([coqui/XTTS-v2 model card](https://huggingface.co/coqui/XTTS-v2)). Read CPML's actual terms before considering XTTS for anything beyond local experimentation.
- **StyleTTS2 pretrained models carry a voice-consent usage clause**, not just a license file: "you agree to only use voices whose speakers grant the permission to have their voice cloned ... or you have to publicly announce that these voices are synthesized" ([yl4579/StyleTTS2 README](https://github.com/yl4579/StyleTTS2)). This is a behavioral obligation, not a code license — easy to miss if you only check the LICENSE file.
- **F5-TTS's training-data (Emilia dataset) licensing terms and how they bind the released checkpoint were not verified this pass — flagged `unknown`, not asserted.** Check before shipping the pretrained checkpoint in a product.
- **Supertonic (`supertone-inc/supertonic`) is being discontinued.** A CAUTION banner added to the README on 2026-07-23 states: "This repository will be archived, and there will be no further development or official support for the open-source Supertonic models... Voice Builder will no longer be accessible after August 31, 2026." ([supertone-inc/supertonic README](https://github.com/supertone-inc/supertonic)). The MIT-licensed weights already published remain legally usable, and sherpa-onnx has already mirrored a converted copy — but don't build a dependency on the upstream `supertonic-py` package or hosted services expecting ongoing support.
- **Kyutai `pocket-tts`'s bundled/downloadable voices are not uniformly licensed with the MIT code.** The README explicitly directs users to check per-voice licensing at [huggingface.co/kyutai/tts-voices](https://huggingface.co/kyutai/tts-voices) before using a given voice ("You can take a look at this page which details the licenses for each voice" — [kyutai-labs/pocket-tts README](https://github.com/kyutai-labs/pocket-tts)). Whichever default voice ships with the plugin needs its specific license checked, not just the repo's overall MIT badge.

## 4. Newer-than-you'd-expect 2026 entrants

- **Kyutai Pocket TTS** (released January 2026) — 100M params, CPU-first, MIT, ~200ms claimed TTFA. Already covered as a top-3 recommendation above; included here because it postdates most "best local TTS" roundups people still cite from 2024–2025.
- **Alibaba Qwen3-TTS** (`QwenLM/Qwen3-TTS`, Apache-2.0, 13k GitHub stars as of this pass) — a streaming, "Dual-Track hybrid architecture" model with a community release thread headlined "Ultra-Low Latency (97ms)" ([r/LocalLLaMA](https://www.reddit.com/r/LocalLLaMA/comments/1qlzbhh/release_qwen3tts_ultralow_latency_97ms_voice/) — could not be scraped for full methodology this pass, treat the 97ms figure as an unverified community-reported claim, not confirmed against Qwen's own docs).
- **Microsoft VibeVoice / VibeVoice-Realtime-0.5B** (`microsoft/VibeVoice`, MIT, 53k stars) — Microsoft's own framing is "Open-Source Frontier Voice AI"; a smaller `-Realtime-0.5B` variant targets the sub-second latency band. Worth a follow-up pass specifically on its Node/TS integration story, which was not established this pass.
